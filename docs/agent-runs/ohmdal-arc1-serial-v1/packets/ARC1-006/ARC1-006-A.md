## Ejecución

Una sola estrategia: **medir el harness tal como está**, sin modificarlo y sin optimizarlo.

- **JS.** Build de producción con la API programática de `vite`, `root` en el repositorio y `outDir`
  en el scratchpad. `manualChunks` separa `node_modules/three` para poder atribuir. Un plugin propio
  vuelca `renderedLength` por módulo en `generateBundle`.
- **Runtime.** Servidor de desarrollo `roxana-dev-alt`, recorrido automático y muestreo con
  `window.advanceTime()` + `window.render_game_to_text()`, que el harness ya expone. `advanceTime`
  fuerza un render sincrónico, así que `renderer.info.render` corresponde a ese frame.
- **Carga.** El build aislado servido como estático desde el scratchpad, leyendo
  `PerformanceNavigationTiming` y `PerformanceResourceTiming`.

`requestAnimationFrame` está throttled en el panel del navegador. Eso **no** invalida el muestreo
—`advanceTime` no depende de rAF— pero sí impide medir fps. No se estima: se declara `not-run`.

Si una dimensión no se puede medir con las herramientas disponibles, el paquete la declara `not-run`
con destino. No se rellena con un número plausible.

## Resultado

`DONE` en ronda 1. La medición produjo tres datos que ningún documento tenía:

1. **Nueve de cada diez bytes de JS del slice son `three`**: 487.112 B de 528.540 B. El código propio
   de doce módulos son 34.474 B. Optimizar el código del slice no mueve la aguja.
2. **El blockout gasta el 0,07 % del presupuesto de triángulos** y el 8,8 % del de draw calls. El
   pico del slice son 22 llamadas y 508 triángulos, ambos en E4.
3. **`vite` inlinea los dos atlas como `data:` URI**: cero requests para textura, pero 6.617 B dentro
   del chunk crítico de arranque y un 23,2 % de sobrecoste por percent-encoding. Registrado en
   `OI-005`.

Hallazgo ajeno adicional: los manifests declaran bytes en LF y el árbol está en CRLF (`OI-004`).
