# ARC1-007 — Montar laboratorio Three.js mediante `RuntimeHost`

**Estado inicial:** `READY`
**Owner:** Director
**Predecesor:** `ARC1-006 — DONE` (`aeb9f70`, presupuesto por escena congelado, `CP-020`)
**Estimación canónica:** 1 d
**Tipo:** runtime. **Primer ticket de esta corrida que cambia código ejecutable.**

## Objetivo verificable

El laboratorio Three.js del slice se **monta y se desmonta a través de `RuntimeHost`**, como un
`ExperienceRuntimeModule` más, sin tocar `/jugar` y sin cambiar qué runtime sirve a Ohmdal en el
juego publicado.

Hoy el laboratorio es un script de módulo con efectos de nivel superior: se ejecuta al importarse,
lee identificadores del HTML de su propia página, registra listeners globales y no se puede
desmontar. Eso lo deja fuera del shell y hace imposible el ticket siguiente: `ARC1-008` mide
`mount → pause → resume → destroy` y fugas ≤ 512 kB por ciclo, y para eso el ciclo tiene que existir.

## Qué exige el canon, literalmente

- doc. 16 línea 58: *«Montar laboratorio Three.js mediante `RuntimeHost` sin tocar `/jugar`»*.
- `docs/3d/STATE.md` línea 117: el alcance máximo de H3 empieza por *«laboratorio Three.js aislado
  bajo `RuntimeHost`, sin alterar `/jugar`»*.
- `docs/ohmdal-biblia/10_VERTICAL_SLICE.md` línea 113: *«Prototipo aislado en Three.js, cargado bajo
  demanda mediante `RuntimeHost` […] Mantener Phaser como baseline de control/causalidad»*.

Las tres frases dicen lo mismo desde ángulos distintos: **bajo demanda, aislado, y sin desplazar a
Phaser**. El laboratorio no reemplaza al runtime cenital; convive con él.

## La decisión de diseño del ticket

`RuntimeHost` resuelve el runtime destino con `experienceById(destination.experienceId).runtime`.
Eso da **un runtime por experiencia**, y el slice necesita **dos para Ohmdal a la vez**: el
`topdown-phaser` que hoy es el producto y el `hd2d-three` que todavía es laboratorio.

Tres caminos posibles, y por qué se elige el tercero:

| Camino | Qué implicaría | Por qué no / sí |
|---|---|---|
| Repuntar `OHMDAL.runtime` a `hd2d-three` | el shell publicado montaría el laboratorio | **No.** Sustituye el juego jugable por un greybox. El veredicto sobre el slice es de `ARC1-030`, no de este ticket |
| Agregar una sexta experiencia `ohmdal-lab` | un mundo falso en el registro de identidades | **No.** `EXPERIENCES` modela los cinco lenguajes jugables; un laboratorio no es un lenguaje. Además obligaría a editar el assert de `tests/a0-experience-registry.test.ts` para que el cambio pase, que es exactamente lo que los gates prohíben |
| `ExperienceLocation.runtime` opcional | quien pide el viaje puede nombrar qué runtime debe servir esa ubicación; por defecto, el del manifest | **Sí.** Es la situación que el canon describe: la misma experiencia con dos gramáticas técnicas durante el slice. El registro de experiencias no se toca, el juego publicado no cambia de runtime y el laboratorio se monta bajo demanda |

Se registra como `CP-021` **al cerrar el ticket** — todavía no está en `DECISIONS.md`. Es una
extensión del contrato P1 (`docs/spec-p1-runtime-host.md`), no una enmienda: sin el campo, el
comportamiento es idéntico al actual.

## Condiciones exactas para `DONE`

- `createOhmdalLab(container)` existe, no tiene efectos de nivel superior y devuelve un handle con
  `pause`, `resume`, `dispose`, `snapshot` y `advanceTime`;
- el laboratorio construye su propia UI dentro del contenedor: no depende de identificadores del
  documento que lo aloja;
- `hd2dRuntime` cumple `ExperienceRuntimeModule` y su `destroy()` deja el contenedor vacío;
- `RuntimeHost` monta el laboratorio cuando la ubicación declara `runtime: 'hd2d-three'`, y sigue
  montando `topdown-phaser` para Ohmdal cuando no lo declara;
- `three` **no** entra al grafo estático del shell: la entrada de `loaders.ts` es un `import()`
  dinámico, verificado en el build;
- el recorrido, la cámara, el HUD y el diagnóstico del laboratorio se comportan igual que antes,
  verificado con `render_game_to_text()` sobre el mismo recorrido determinista;
- existe evidencia de un ciclo `mount → destroy → mount` sin excepciones en consola —**medición
  informativa, no el gate de fugas**, que es de `ARC1-008`—;
- `npm run build`, `npm test`, `npm run 3d:validate-manifests` y `git diff --check` PASS;
- diff dentro del ownership declarado arriba;
- todo hallazgo ajeno queda en `OPEN_ISSUES.md` y **no se arregla**;
- `CP-021` registrada en `DECISIONS.md`;
- commit acotado creado;
- `ownership.json` rotado a `ARC1-008` como parte del cierre (`CP-017`);
- `ARC1-008` pasa a `READY`.

## Rollback

Un commit correctivo devuelve `main.ts` del laboratorio a su forma anterior; el campo
`ExperienceLocation.runtime` es opcional y aditivo, así que revertirlo no afecta al shell publicado.
No se borra evidencia ni se reescribe historia.
